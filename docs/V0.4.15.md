# v0.4.15 — Issue-driven execution

v0.4.15 makes an **existing GitHub issue** a first-class input to the Harness while preserving the existing trust hierarchy: the remote issue is fetched and frozen, then a sealed QuickContract or SDD/TaskContract becomes normative for the active run.

## Goal

A user or Paseo-hosted lead can say:

> Implement issue #142.

The operational equivalent is:

```bash
aeh issue implement 142
```

or:

```bash
aeh run --issue 142
```

The user does not need to manually create an SDD, duplicate the issue, create a branch, create a worktree, select implementers or manage the review/remediation loop.

## Lifecycle

```text
GitHub issue
   |
   v
fetch + validate issue identity/state
   |
   v
freeze title/body + SHA-256 snapshot
   |
   v
intake evidence
(paths, labels/domains, risk, acceptance, flags)
   |
   v
read-only planner normalization when non-trivial
   |
   v
deterministic QUICK/SPEC decision
   |
   +--> QuickContract
   |
   `--> complete SDD + TaskContract + Gherkin
             |
             v
       validate + seal
             |
             v
bind EXISTING issue to delivery state
             |
             v
reuse/create issue-linked branch
             |
             v
optional Paseo worktree
             |
             v
normal aeh run lifecycle
             |
             v
deterministic validation -> reviews -> convergence -> lead acceptance
```

## CLI

### Inspect

```bash
aeh issue inspect 142
```

Fetches the issue and shows preliminary QUICK/SPEC evidence without creating a TaskContract.

### Import/freeze

```bash
aeh issue import 142
```

Creates `GH-142` as a sealed task without executing implementation.

For explicit issue revision acceptance:

```bash
aeh issue import 142 --refresh
```

If an active Paseo delivery workspace already exists, refresh is blocked unless explicitly forced:

```bash
aeh issue import 142 --refresh --force
```

### Complete execution

```bash
aeh issue implement 142
```

Equivalent entrypoint:

```bash
aeh run --issue 142
```

Optional profile:

```bash
aeh issue implement 142 --profile maximum-quality
```

## Repository resolution

The issue repository is resolved from:

1. `delivery.github.repository` when configured;
2. otherwise the repository's `origin` remote.

The issue endpoint rejects GitHub pull requests returned from `/issues/<number>`; issue-driven execution is intentionally issue-specific.

Public issues may be fetched without authentication. Private repositories require a usable token. Token resolution follows the delivery configuration and environment:

```text
configured tokenEnv
GH_TOKEN
GITHUB_TOKEN
GITHUB_PAT
```

Tokens are never serialized into the issue snapshot, TaskContract or delivery state.

## Frozen issue source

The Harness stores:

```text
.harness/issues/GH-142.json
```

with:

- repository;
- issue number and URL;
- title/body;
- state;
- labels;
- created/updated/fetched timestamps;
- SHA-256 of normalized title/body.

The TaskContract records the same source identity and fingerprint.

Only **title and body** are treated as normative remote content for the hash. Labels can influence initial routing/triage but changing a label does not silently rewrite requirements. Comments are not incorporated into the active normative contract unless a later intake version explicitly adds that policy.

## Planner normalization

Non-trivial issues or issues without directly extractable acceptance statements can be sent to the configured read-only planner:

```yaml
workflow:
  issueIntake:
    plannerAgent: planner
```

The planner may inspect repository code/tests/architecture to derive implementation detail and existing invariants. It returns a machine-validated intake structure containing:

- problem / desired outcome;
- explicit or repository-derived requirements;
- acceptance scenarios;
- scope/domains;
- risk and escalation flags;
- compatibility/dependency/schema constraints;
- proposed implementation design;
- implementation tasks and non-goals;
- unresolved decisions.

The planner cannot directly write normative artifacts. The Harness validates its structured output and writes the QuickContract/SDD itself.

If the planner runtime fails or returns invalid output, deterministic extraction provides a fallback rather than making the intake dependent on one LLM session.

## Product-decision boundary

The planner/intake distinguishes:

```text
ready
requires_product_decision
spec_contradiction
```

Repository-derived implementation details are allowed when supported by existing evidence. Product/business choices that cannot be determined from the issue/repository are not invented.

Those become:

```text
REQUIRES_PRODUCT_DECISION
```

Contradictory authoritative intent becomes:

```text
SPEC_CONTRADICTION
```

Both follow the Harness human-on-exception policy.

## QUICK vs SPEC

The issue is passed through the same deterministic triage rules used by normal requests.

A QUICK result still requires:

- explicit bounded file scope;
- low risk;
- no security/auth/architecture/schema/migration/public API/new-dependency escalation signals;
- observable acceptance statements.

Anything outside that boundary becomes a full issue-derived SDD.

Issue-derived SDD requirement IDs are stable:

```text
GH-142-R1
GH-142-R2
...
```

The generated proposal/spec/design/tasks/Gherkin/TaskContract must pass the ordinary traceability validator before sealing.

## Existing issue reuse

Issue-driven intake calls `seedDeliveryRecordFromIssue` with the existing issue identity.

Therefore downstream handoff **does not create another issue**.

```text
GitHub #142
    |
    v
GH-142 delivery record
    |
    v
handoff sees issueNumber=142
    |
    v
skip issue creation
```

This makes the new intake path compatible with the v0.4.14 downstream delivery machinery.

## Branch reuse

The configured branch pattern remains:

```yaml
delivery:
  github:
    branchPattern: feature/gh-{issue}-{slug}
```

For an existing issue the Harness first checks the exact remote ref. If it already exists, it reuses that branch. Otherwise it creates it from the captured originating/base branch.

No force push, amend or rebase is used as part of intake recovery.

## Paseo worktree

When Paseo delivery is enabled, issue-driven handoff reuses the v0.4.14 worktree mechanism:

```text
issue -> existing/new branch -> Paseo checkout-branch worktree
```

The sealed task context, including the issue snapshot, is materialized into the worktree. Implementation, deterministic validation, review, remediation and Graphify execute against that workspace while control state remains in the original checkout.

## ISSUE_DRIFT

Before each issue-derived run, the Harness re-fetches the issue title/body and recalculates the fingerprint.

If the fingerprint differs from the frozen TaskContract:

```text
ISSUE_DRIFT
```

The active run is not silently reinterpreted.

This protects against a common failure mode:

```text
agent begins requirement A
issue edited to requirement B
agent unknowingly continues using mixed A/B context
```

Instead the user/lead explicitly accepts the revised source with `--refresh` when appropriate.

## Configuration

Default initialized projects include:

```yaml
workflow:
  issueIntake:
    enabled: true
    snapshotDir: .harness/issues
    verifyDriftOnRun: true
    requireOpen: true
    plannerAgent: planner
    autoHandoff: true
```

`autoHandoff` means issue implementation invokes the configured delivery flow automatically when GitHub/Paseo delivery is enabled. It does not turn remote delivery on by itself: `delivery.github.enabled` and `delivery.paseo.enabled` remain explicit project choices.

## Trust hierarchy

For issue-driven work:

```text
GitHub issue at intake time
        |
        v
frozen issue snapshot
        |
        v
sealed QuickContract / SDD + TaskContract
        |
        v
implementation and validation
```

During the active run:

```text
sealed TaskContract/SDD > mutable remote issue > agent memory/summaries
```

The remote issue remains provenance and collaboration input; the frozen/sealed contract prevents mutable requirements during execution.

## Natural-language/Paseo behavior

The `engineering-workflow` skill recognizes existing-issue implementation intent. A lead started from Paseo mobile should translate:

> Implement issue #142.

into:

```bash
aeh issue implement 142
```

The same command owns intake, freeze, optional handoff/worktree and the normal autonomous engineering workflow. The lead should not ask the user to manually perform intermediate Harness commands unless a genuine human-on-exception state is reached.
